# Playtest notes — 2026-08-05 (co-op, 2 players)

Source: a two-player co-op session over the P2P (host-authoritative WebRTC) build —
one host, one guest. This was the first real co-op test of the P2P transport under
movement load, and the dominant signal is that the **guest experience** is where the
seams are: the host (authoritative) sees a clean game, the guest sees rubber-banding.

Feedback sorted into buckets as with [playtest-2026-07-20.md](playtest-2026-07-20.md)
and [playtest-2026-07-27.md](playtest-2026-07-27.md). Items already fixed in this pass
are marked ✅ **FIXED**.

---

## 1. Critical bugs

Ordered by how badly they break a session.

| # | Bug | Detail | Status |
|---|---|---|---|
| C1 | **Guest position rubber-banding** | The guest snaps back to a prior position mid-movement, frequently enough to make the game unplayable for the non-host. The host sees no issue (it's authoritative). Root cause is almost certainly the prediction/reconciliation gap in the P2P transport — the guest either isn't predicting locally, or predicts and then hard-snaps to each authoritative correction instead of smoothing. | **OPEN — roadmap.** This is the guest-prediction polish already flagged as the remaining P2P work. Needs a dedicated pass: local input prediction on the guest + smoothed reconciliation (lerp/replay rather than hard snap). Not a quick fix. |
| C2 | **Enemies retain aggro after player death** | A downed player still held enemy threat; enemies kept attacking the corpse instead of pivoting to the living survivor. | ✅ **FIXED** — both target-selection paths now skip downed players: `Enemy.pickTarget` (regular/casting/approach-cast enemies) and `Enemy.closestPlayer` (bosses). A downed player is a corpse, not a threat — aggro pivots to a living survivor the instant a teammate goes down, and an enemy whose only in-range target is downed drops back to patrol. Regression tests in `tests/engine/enemy.test.ts`. |
| C3 | **Can't start a second run without a full page reload** | After a co-op run ends, the host cannot create or join a new online room without `Cmd+R`. Reported as a `Party` teardown gap, but the real cause was client-scene state: `BrowseScene.joining` is an instance field, and Phaser reuses the scene instance across `scene.start`, so field initializers run only once. A successful host/join set `joining = true` and hopped to the lobby; nothing reset it (the `SHUTDOWN` handler cleared the timer and panel, not the flag). Re-entering "Play Online" after a run ran `create()` on the same instance with `joining` still `true`, so every host/join attempt hit the early return and silently did nothing — only a reload, which rebuilds the instance, cleared it. | ✅ **FIXED** — reset `this.joining = false` at the top of `BrowseScene.create()`, per the reset-in-`create()` convention. |

## 2. Design feedback

| # | Item | Detail |
|---|---|---|
| D1 | **Room enemy profiles ("mob voices")** | Rooms felt chaotic with fully-random mixed spawns. Proposal: define 2–3 curated enemy combos ("mob voices") per room — e.g. *enchanter + flyers*, *frog-flowers + one other* — and roll randomly *within* a chosen profile. Keeps variety without all-random chaos. `SpawnDirector` is the right home: the enemy-pool + count logic becomes a roll over a small set of profiles rather than a flat weighted draw. Fits the OO ethos — a profile is a small class/const list of enemy classes, not a config blob. |
| D2 | **Enemy stacking / no mutual collision** | All enemies can occupy the same tile and attack simultaneously, which removes counterplay. Players want enemies to spread out or path *around* to surround them — enabling the bunch-for-cleave vs. spread-to-surround decision. Options: enable enemy–enemy collision (matter-js filters already exist in `PhysicsWorld`), or add a spread/surround steering behavior on top of the flow field. Needs a design+perf pass (enemy–enemy collision multiplies solver cost; steering is cheaper but fuzzier). |
| D3 | **Dead-player spectate mode** | Downed/dead players have nothing to do while waiting for a revive or run end. A spectate/free-look (or follow-a-teammate) camera would fill the gap. Low urgency, flagged. |

---

## 3. Takeaways

- The **P2P guest path is the priority** — C1 (guest rubber-banding) is the one
  remaining run-ender and needs a focused pass on guest prediction + smoothed
  reconciliation. C3 turned out to be a client-scene state bug (fixed), not the P2P
  teardown it was first read as.
- The core loop and combat held up; the design feedback (D1–D3) is enrichment, not
  repair — the game is playable, it wants more intentional encounters and more to do
  when downed.
